مستندات کامل API پنل MWPanel (Backend Go + Echo v4)
===============================================================================
این سند با خواندن مستقیم کد منبع (نه حدس) تهیه شده: فایل اصلی مسیرها
D:\بنل وایرگارد\MWPanel-main\api\http\api.go و تمام فایل‌های handler/schema
زیر api\http و api\http\schema به‌صورت کامل بررسی شدند.

-------------------------------------------------------------------------------
۰) معماری کلی
-------------------------------------------------------------------------------

فریم‌ورک: Echo v4 (github.com/labstack/echo/v4) + echo-jwt/v4 برای JWT
ماژول: github.com/maahdima/mwp/api

آدرس پایه: تمام endpoint های API زیر پیشوند  /api  ثبت شده‌اند
(router := app.Group("/api") در api/http/api.go).

سرو کردن رابط کاربری (React/Vite): مسیر GET /* (خارج از گروه /api، بدون
احراز هویت) در api/http/ui.go — کل SPA را سرو می‌کند، با cache دائمی برای
/assets/* و no-cache برای index.html.

قالب پاسخ استاندارد (از schema/common.go):
    موفق بدون داده:
        {"statusCode":200,"status":"success"}
    موفق با داده:
        {"statusCode":200,"status":"success","data":{...یا [...]}}
    خطا:
        {"statusCode":<۴۰۰/۴۰۱/۴۰۳/۴۰۴/۵۰۰...>,"status":"error","message":"..."}

نکته: بعضی endpoint ها به‌جای JSON، فایل خام (raw file/stream) برمی‌گردانند
(مثلاً دانلود کانفیگ، QR کد، بک‌آپ، اکسل) — این موارد در جدول‌ها با عبارت
«raw file» یا «raw stream» مشخص شده‌اند.

-------------------------------------------------------------------------------
۱) لایه‌های احراز هویت (۴ نوع کاملاً مجزا و غیرقابل‌تعویض با هم)
-------------------------------------------------------------------------------

۱.۱) JWT ادمین/ریسلر (اصلی‌ترین)
    - با echojwt.WithConfig، کلید امضا از authenticationService.AccessSecret
    - روی اکثر گروه‌های مسیر اعمال می‌شود (نه سراسری — هر گروه جداگانه)
    - هدر درخواست: Authorization: Bearer <token>
    - Claim های داخل توکن شامل role ("admin" یا "reseller") و در صورت
      ریسلر بودن، reseller_id
    - شکست احراز هویت -> 401 عمومی "Unauthorized"

۱.۲) JWT اپلیکیشن موبایل (کاملاً جدا، غیرقابل تعویض با JWT بالا)
    - کلید امضای مستقل (AppAuthController.AppJWTConfig()، نه
      authenticationService.AccessSecret)
    - فقط روی گروه /app اعمال می‌شود
    - Claim ها: sub=نام‌کاربری، role=app_user، application_id
    - توکن‌های این دو سیستم به‌هیچ‌وجه با هم قابل استفاده نیستند

۱.۳) کلید API خارجی (X-Api-Key)
    - فقط روی گروه /api/external اعمال می‌شود
    - هدر: X-Api-Key: <key>  (نه Authorization: Bearer)
    - تأیید از طریق apiKeyService.Verify(key)، شکست -> 401

۱.۴) توکن پشتیبانی (Support Token)
    - فقط روی GET /api/support/logs
    - هدر: Authorization: Bearer <token>   (ولی این یک JWT نیست! یک توکن
      ساده‌ی تولیدشده توسط ادمین است که از طریق tokenService.Verify چک
      می‌شود)
    - تمام دلایل شکست (گم‌شده/منقضی/نامعتبر) به یک ۴۰۱ عمومی تبدیل می‌شوند
      (نمی‌توانید از روی پاسخ تشخیص دهید کدام مورد بوده)

۱.۵) میان‌افزار بررسی لایسنس (سراسری، قبل از همه‌چیز)
    - اگر licenseService.IsBlocking() باشد (نصب بدون لایسنس، لغو شده،
      منقضی، یا سرور لایسنس غیرقابل‌دسترس بعد از مهلت)، **تمام** ترافیک
      API با خطای زیر رد می‌شود:
        HTTP 403
        {"statusCode":403,"status":"error","message":"...",
         "error_code":"license_invalid"}
    - مسیرهای معاف (باید همیشه کار کنند حتی بدون لایسنس معتبر):
        /api/license/activate
        /api/license/trial
        /api/support/logs
        /api/user/:uuid/...  (تمام مسیرهای share-link کاربر نهایی)

۱.۶) میان‌افزار اتصال کلاینت (ClientConnectionMiddleware) — نه احراز هویت
    - این یک چک «زنده بودن اتصال» است، نه یک چک هویتی
    - اگر پنل در حال حاضر به پروسه‌ی مدیریتی WireGuard/User-Manager روی
      دستگاه RouterOS وصل نباشد، با خطای زیر رد می‌شود:
        HTTP 503
        {"statusCode":503,"status":"error","message":"Client is not connected to the server"}
    - روی گروه‌های زیر اعمال می‌شود (بخشی یا کامل): interface، peer
      (بیشترشان)، device، sync، user-manager/account (بیشترشان)،
      user-manager (گروه/پروفایل)

۲) کمک‌تابع‌های تشخیص نقش (برای فهمیدن ستون «احراز هویت» در جدول‌های پایین)
-------------------------------------------------------------------------------

    forbidUnlessAdmin(ctx)
        -> ۴۰۳ مگر role=="admin"

    peerScopeFromContext(ctx)
        -> برای ادمین: nil برمی‌گرداند (بدون محدودیت، همه چیز را می‌بیند)
        -> برای ریسلر: reseller_id خودش را برمی‌گرداند (۴۰۳ اگر توکن
           reseller_id نداشته باشد)
        این الگوی «ریسلر-یا-ادمین با محدوده‌ی خودکار» در بیشتر منابع
        (peer، application، v2ray-package، dns-account، ...) استفاده شده

    adminResellerIDFromParam(ctx)
        -> ۴۰۳ برای هر تماس‌گیرنده‌ای با role=="reseller" (بدون قید و شرط)
        -> سپس :reseller_id را از مسیر URL می‌خواند
        این الگو برای مسیرهای «ادمین به‌جای یک ریسلر خاص کاری انجام می‌دهد»
        (مثل /peer/reseller/:reseller_id/...) استفاده می‌شود

    requireAdminScope(ctx)
        -> ۴۰۳ اگر role=="reseller"
        برای مواردی که با وجود در دسترس بودن کلی endpoint برای ریسلر، یک
        اقدام خاص (مثلاً ریست کردن مصرف خودش) فقط برای ادمین مجاز است —
        تا ریسلر نتواند مصرف خودش را درست قبل از صورت‌حساب صفر کند

    getRoleAndResellerFromContext(ctx) / getRoleFromContext(ctx)
        -> صرفاً خواندن خام role و reseller_id از claim های JWT

۳) فهرست کامل Endpoint ها به تفکیک حوزه
-------------------------------------------------------------------------------
نکته‌ی مهم: ستون «ورودی»/«خروجی» نام ساختار (struct) واقعی در کد Go است؛
شکل دقیق JSON هر ساختار را باید در فایل schema مربوطه (زیر
api/http/schema/) بررسی کنید اگر نیاز به فیلدهای دقیق دارید. اینجا تمرکز
روی مسیر، متد، رفتار، و سطح دسترسی است.

۳.۱) AUTH  (/auth)
===============================================================================
POST /auth/login
    توضیح: اعتبارسنجی یوزرنیم/پسورد؛ اگر OTP فعال باشد فقط OtpRequired+
           OtpToken برمی‌گرداند (نه توکن واقعی)؛ وگرنه جفت توکن کامل.
           شکست مکرر -> ۴۲۹ (ErrOtpBanned). شکست دیگر -> ۴۰۴ + هشدار
           تلگرام ناهمگام (اگر بات تنظیم شده). موفقیت بدون OTP -> هشدار
           ورود ناهمگام (به چت ریسلر اگر role=="reseller"، وگرنه ادمین).
    ورودی: LoginRequest   خروجی: BasicResponseData[LoginResponse]
    دسترسی: عمومی (این خودِ ورود است)

POST /auth/otp/verify
    توضیح: مرحله‌ی دوم ورود (تکمیل OTP)؛ ۴۲۹ در صورت بن، ۴۰۱ در صورت کد
           نامعتبر/منقضی؛ موفقیت = همان هشدار ورود مثل بالا.
    ورودی: VerifyOtpRequest   خروجی: BasicResponseData[LoginResponse]
    دسترسی: عمومی

PUT /auth/profile
    توضیح: تغییر یوزرنیم/پسورد خودِ کاربر؛ شناسه‌ی حساب همیشه از claim
           "sub" توکن JWT گرفته می‌شود (هرگز از ورودی کاربر) — یعنی هر
           کاربر فقط می‌تواند حساب خودش را عوض کند. اگر ریسلر باشد، یک
           رکورد audit log ثبت می‌شود.
    ورودی: UpdateProfileRequest   خروجی: BasicResponse (بدون داده)
    دسترسی: هر کاربر احراز هویت‌شده (فقط خودش)

GET /peer/activity/resellers    -> رتبه‌بندی فعالیت همه‌ی ریسلرها (صفحه‌بندی‌شده). ادمین‌فقط.
GET /peer/activity/self

    ادمین یک reseller_id واحد ندارد)

POST /peer/reseller/:reseller_id           -> ایجاد peer برای ریسلر مشخص. ادمین‌فقط.
PUT /peer/reseller/:reseller_id/:id        -> به‌روزرسانی به‌نمایندگی از ریسلر. ادمین‌فقط.
DELETE /peer/reseller/:reseller_id/:id     -> حذف به‌نمایندگی. ادمین‌فقط.

۴) نکات و ناسازگاری‌های جالب کشف‌شده از کد (برای توسعه‌دهنده‌ی MWPanel مفید است)
-------------------------------------------------------------------------------

۴.۱) tunnel-health روی سطح گروه هیچ میان‌افزار ادمینی ندارد، ولی هر ۱۷
     handler جداگانه forbidUnlessAdmin را خودشان صدا می‌زنند — نتیجه‌ی
     نهایی یکسان (ادمین‌فقط) است، فقط الگوی پیاده‌سازی‌اش فرق دارد.

۴.۲) user-manager/protocol-config: دو endpoint دانلود (گواهی و فایل
     کلاینت) طبق کامنت کد باید ادمین‌فقط باشند، ولی تابع مشترکی که صدا
     می‌زنند هیچ چک نقشی ندارد — یعنی در عمل هر کاربر احراز هویت‌شده
     (ریسلر هم) می‌تواند این دو فایل را دانلود کند. این را هنگام طراحی
     لایه‌ی امنیتی MWPanel در نظر بگیرید.

۴.۳) wallet: پاسخ GetWalletBalance یک map[string]interface{} دستی است،
     نه ساختار schema.WalletResponse که در کد تعریف شده ولی استفاده
     نمی‌شود (کد مرده).

۴.۴) سه حوزه‌ی بسته‌ی ترافیک (traffic-package، user-manager-traffic-
     package، v2ray-traffic-package): مسیرهای purchase و
     purchases/self هر سه **فقط برای ریسلر** هستند و ادمین صراحتاً رد
     می‌شود — برعکس اکثر الگوهای دیگر کد که ادمین همیشه زیرمجموعه‌ی
     بزرگ‌تری از دسترسی ریسلر دارد.

۴.۵) pricing/plan: لیست‌کردن و دیدن جزئیات یک طرح برای هر دو نقش (ادمین
     و ریسلر) باز است، فقط ایجاد/ویرایش/غیرفعال‌سازی ادمین‌فقط است.

۴.۶) invoice: تنها عملیات نوشتنی که ریسلر مالک فاکتور هم مجاز به انجامش
     است، پرداخت (pay) است؛ ایجاد/صدور/لغو همه ادمین‌فقط هستند.

۴.۷) license/public-status: برخلاف license/activate و license/trial که
     کاملاً از بلاک لایسنس معاف‌اند، این یکی چک جداگانه‌ای ندارد — رفتار
     دقیقش را اگر نیاز بود باید مستقیم از کد تأیید کنید.
